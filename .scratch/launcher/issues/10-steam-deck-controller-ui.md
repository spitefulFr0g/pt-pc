No human or physical-device test may be a release gate. Record what simulated/virtual environments actually exercise; they do not establish unperformed physical hardware validation. Identify a concrete standalone controller-input approach compatible with the approved C++/Qt Widgets boundary, supported by repository/official API evidence; investigate externally if needed. Keep game/engine code unchanged.

Account for Steam launching the optional GUI as a non-Steam game, game-window focus after Play, preserving controller input for the game, the independently closable launcher, and returning to the launcher without creating a second game instance. Define any one-time Steam setup plainly and do not silently add entries to a user's Steam library. Resolve startup/session choices necessary for a buildable specification; a non-Steam shortcut alone is not proof of Gaming Mode compatibility.

## Answer

Keep the selected G layout/artwork, gothic title and stable Play label. Add a visible controller focus ring and small contextual A/B/X hints. D-pad/left stick move, A activates, B goes back, X edits a text field. Scroll focused items into view, skip disabled controls, and restore the previous valid focus on returning. Pointer and keyboard stay usable.

Use controller-friendly **in-app file/folder browsing and a built-in keyboard**, keeping setup usable without Steamworks keyboard initialization, a Steam overlay, or an external keyboard. Done applies a draft; B discards it and restores field focus. Back during preparation or after unsaved settings opens a safe-default confirmation; progress/completion must not steal focus or leave stale prompts. Keep readiness/recovery actions reachable through the same controller actions.

Use **SDL3 release-3.4.16 directly in the standalone Qt launcher**, without pt_engine or video/renderer initialization. A bounded GUI-thread QTimer pumps gamepad events into shared normalized UI commands. Qt application/window activity and session state explicitly gate controller dispatch; SDL's background hint alone cannot handle Qt-only windows. Clear held/repeat state on deactivation and require neutral before controller rearming. Keyboard/pointer are separate normal UI inputs and remain usable after controller disconnect. Release/reopen launcher controller handles around game handoff/foreground return. Use the non-Steam shortcut's standard Steam Gamepad profile once through SDL's emulated-gamepad path, with the launcher's raw Deck HIDAPI driver disabled locally; do not leak launcher hints into the game or fabricate a Steam App ID.

Steam starts a **small launcher-owned Linux session supervisor**. The supervisor owns process/session identity, IPC and bundle coordination, and remains alive while its GUI, game or managed job needs it. It keeps the game in the same supervised session while allowing the GUI to background or close independently. Qt startDetached alone cannot override an external Gamescope reaper. A newly invoked launcher reconnects to that bundle's session rather than starting another game. Use real process handles/start identity plus the bundle lock; PID alone is insufficient. Follow the accepted managed-job cancellation/journal/recovery policy when a busy GUI closes or crashes.

Use an explicit Gaming Mode session entry point/argument for Steam's non-Steam shortcut rather than guessing from a distro name. Keep the supervisor free of GUI/controller ownership; it supplies the original launch environment to the game and a private Qt/plugin environment to the GUI. During a Linux Gaming Mode self-update, keep Steam's primary process alive: after all game/jobs stop and the transaction helper replaces verified files, the supervisor uses an exec-style takeover into the verified new supervisor at the same PID, carrying a bounded local transaction/session handoff. The new helper starts the GUI and completes startup acknowledgement; startup failure follows journal/backup recovery. Do not exit the old root and spawn a replacement child that the Gamescope reaper would immediately terminate. Automate same-PID takeover/recovery; Windows retains its platform replacement helper behavior. [Linux exec semantics](https://man7.org/linux/man-pages/man2/execve.2.html) explain replacement without creating a new PID.

After Play, give the game foreground/input ownership and leave the GUI in the background. If the GUI is still open, restore it after the game exits and require neutral controller input before rearming. If the compositor brings the GUI forward during play, focus Return to game, block duplicate launch/settings writes/updates, and resume the existing process. Preserve a known flat fallback and its continue/retry flow. Closing only the GUI leaves a live game running; after the last GUI/game/job ends, the session helper exits. Intentional Steam Stop/session shutdown retains normal platform behavior. Do not silently mutate Steam library entries; document the one-time non-Steam shortcut pointing at the session entry point. Do not promise a particular Steam window-switch UI without evidence.

Implement all required tests as **agent-run automation**: Qt UI/event-loop focus and controller-flow checks; actual SDL adapter checks with virtual joystick/button/axis injection; session/IPC/subprocess/window fixtures for startup failure, close/crash/reconnect/exit/shutdown; and nested Gamescope integration in an agent-runnable environment. Record actual versus simulated/Steam-client coverage and close any mandatory harness gap through implementation or a concrete tooling blocker. No human, physical Deck/controller or headset check is a release gate.
