## Question

What concrete evidence will be sufficient to call the first personal launcher ready on Linux and Windows, in flat and VR modes? Choose the concrete platform package formats and optional shortcuts, then specify target environments, physical-headset checks versus simulated checks, installation/repair/settings preservation scenarios, and which launch/package artifacts must be exercised.

Account for the agreed update policy, upstream integration boundary, and any validation the agent cannot perform without the user's hardware. Separate an untested target from a verified one. Establish the acceptance criteria and implementation handoff, not the implementation itself.

## Answer

### Packages and targets

Ship a Windows x64 ZIP and Linux x86_64 tar.gz with the launcher, matching native game runtime, self-contained extraction helper, required redistributable dependencies, and license/source notices. Player-owned game archives are supplied locally. Preserve the approved portable layout, Linux executable permissions, and adoption of existing single/dual-platform bundles. The portable folder opens directly; desktop shortcuts are optional and created on request. Moving a bundle can require recreating shortcuts. Do not silently add Steam library entries.

Target Windows 11 x64, SteamOS Stable x86_64 on Steam Deck, and Omarchy Stable x86_64 on the user's Surface. SteamOS **Gaming Mode and controller navigation are required first-release functionality**; also preserve ordinary desktop/pointer/keyboard operation. Omarchy's acceptance scope is launcher/preparation/settings/update operation under Hyprland; Surface gameplay is not a requirement. Native Linux VR remains a planned experimental capability, subject to the unchanged-game/build-only integration boundary.

Pin shared Qt 6.12.0 initially and record the exact kit/build and dependency inventory. Use MSVC 2022 on Windows and a pinned compatible Linux build environment. Keep Qt's linkage requirements scoped to launcher targets instead of inheriting incompatible global game flags. Audit all shipped ELF GLIBC/GLIBCXX/CXXABI requirements against chosen stable target environments; arbitrary newest Arch packages are not the Omarchy Stable baseline. Deploy matching Qt platform plugins and dependencies for Wayland and xcb. SteamOS operation must work in a writable user-owned folder without root, pacman installation, or disabling system read-only protection. Host GPU drivers and configured VR services remain system prerequisites.

Record exact OS builds/channels/package snapshots, desktop/compositor/backend, toolchain, runtime/launcher versions, upstream revision and package hashes for every actual build/test. Research-time version references are not test results or blanket promises about future rolling updates. Keep the registered Virtual Desktop OpenXR runtime as configuration evidence only; the launcher does not change global runtime selection automatically.

### Acceptance policy

**All required checks are automated and agent-run. No human test, physical device, headset session, or manual signoff is a release gate.** This is the user's final explicit instruction and supersedes all earlier physical/manual gating proposals in this ticket and linked decisions.

Windows may release when its automated gates pass. A Linux preview must include the required Gaming Mode/controller implementation and corresponding automated coverage; it cannot defer that functionality to a later feature release. Linux release claims and promotions follow its automated artifact/integration results. Keep unexercised environments and physical VR status explicit in the evidence record; do not label a simulator, WSL session or virtual display as a physical Steam Deck/headset pass. Missing hardware does not prevent release acceptance. Optional later hardware observations may extend evidence but are never required from the user.

Use Pass, Fail or Not run per check, naming the actual environment, procedure, artifact identity, expected/observed result and log/artifact location. Automated success describes what the test exercised. An unrun mandatory automated check remains pending/failing acceptance rather than becoming a request for the user to test it. Agents must provide/repair the automated harness or report a concrete tooling blocker. No production launcher, package, gameplay or headset acceptance check has been executed in this planning work.

### Automated behavior coverage

Test public launcher operations through disposable bundles and controlled filesystem/helper/process/network/controller boundaries. Reuse existing installer, synthetic extraction, settings, presets, process/lock and signed-release checks where appropriate. Verify externally observable effects and preserved files rather than mirroring private implementation. Run focused existing upstream checks for reused code and preserve ordinary game builds without a Qt dependency.

Required scenarios:

- Offline preparation from supported dump/fPKG fixtures, existing-archive adoption without unnecessary re-extraction, progress/cancel and recovery, missing/corrupt source, destination errors/space exhaustion, moved bundles, non-ASCII/spaced paths, known/unknown runtime adoption and explicit recoverable runtime alignment.
- Edited-key-only INI updates, preset semantics, preservation of unknown/unexposed keys by launcher writes, concurrent file edits, no competing writes during a game session, correct per-launch flat/VR flags and bundle-relative paths. Preserve the user-approved limitations of unchanged game serialization and enhanced-texture-cache placement.
- Independent flat/VR readiness, proven blockers versus unknown/Try anyway, bounded probes, fresh-launch log parsing, known fallback and process failures, unchanged flat fallback, no duplicate sessions, independent launcher closure/reopening, and direct/script process activity. A process start or XR session object must never be asserted as headset presentation.
- Manual Check then Install only, offline launch availability, dedicated downstream channel filtering, invalid signatures/hashes/platforms/mixed pairs, containment and staging, preserving archives/source/saves/mods/settings/unowned files, Windows files in use, running-game checks, interrupted replacement/recovery, startup acknowledgement and rollback. Use disposable fixtures for destructive failure cases.

### GUI, controller and session coverage

Exercise the real Qt UI/event loop with automated input and focus assertions, visual captures and accessible controls. Preserve the selected G artwork/layout, gothic title, stable Play label and absence of routine ready/running filler. Check scaling, resizing, keyboard access, dialogs, setup/settings/update flows and visible errors without initializing the game renderer. Include native packaged-UI smoke tests on available Windows/Linux automation environments, with explicit backend/session information; offscreen tests alone do not establish native plugin loading.

For Steam Deck Gaming Mode, automate directional focus, activate/Back, scrolling, file selection and keyboard-entry behavior, preparation/cancel, settings, updates/recovery, game handoff/window focus, return and independent launcher/game lifetime. Inject controller input through the chosen real input adapter where possible; separately test session/process integration with a controlled game-window helper. Exercise Gamescope/session behavior in an agent-runnable environment where feasible, reporting actual compositor/Steam versus simulated boundaries. Do not require a person to operate Steam, a Deck or an on-screen keyboard to pass these tests. Exact input/session design and the feasible automation seam must be resolved in [Design Steam Deck Gaming Mode and controller navigation](10-steam-deck-controller-ui.md).

For Omarchy, cover Hyprland/Wayland-compatible focus, tiling/resizing, scaling, dialogs and safe preparation/settings/update operations. Use pinned target-compatible automated environments and fixtures; record any environment not actually exercised rather than claiming Surface validation. Keep the actual game's controls/behavior unchanged.

### Packaged artifact and runtime coverage

Check built release archives after extraction in clean agent-run target-compatible environments, without Qt/.NET SDK or developer PATH/library leakage. Verify permissions, dependency/plugin discovery, runtime search paths, bundled extractor operation, required notices/source availability, explicit missing-system-prerequisite handling and offline setup/play-path behavior. Use appropriate virtual displays/compositors and software graphics for automation where supported, identifying them in results. Packaging verification is distinct from full real-game or headset evidence.

Use existing headless XR and synthetic readiness/process evidence for VR automation; include negative loader/runtime/session/fallback cases. Run available upstream automated runtime/renderer checks relevant to the paired build. Full proprietary game data is not distributed or required in public CI. Where a controlled game process/archive fixture supplies a test boundary, name it as such. No physical gameplay, headset comfort judgment, or user-run gameplay session is required.

The next design ticket must produce a concrete Gaming Mode/controller interaction and input/session plan with an automated test approach. This release decision is resolved; the map remains open until that new scope is specified. Then synthesize the linked decisions into the implementation specification and tracer-bullet tickets. Do not treat these decision tickets or the HTML study as production launcher code.


The controller/session design is now resolved in [Design Steam Deck Gaming Mode and controller navigation](10-steam-deck-controller-ui.md), including the actual SDL adapter, session-helper process and takeover boundaries, and their agent-run automation seams. This resolves a planning dependency; it does not claim native implementation tests have run.
