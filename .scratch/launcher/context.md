# Launcher starting points

Repository observations for planning, not architecture decisions. Inspected at base commit `d0a9b8f` on branch `launcher`.

- The existing Windows setup is a Win32 GUI; Linux setup uses a terminal or optional Zenity dialogs. Both use shared installation logic. See [Installer documentation](../../docs/installer.md), [Windows setup](../../installer/Native/setup.cpp), [Linux setup](../../installer/Native/setup_linux.cpp), and [Shared installation code](../../installer/Native/setup_core.h).
- Shared installation code already covers source recognition, archive copying, manifests, staged installation, repair/update swaps, and rollback. The architecture decision must determine which interfaces can be reused without tying launcher UI to the game renderer.
- The source also has [first-run source selection](../../src/game/first_run.cpp) and [shared updater code](../../installer/Native/updater_core.h); the README and installer prose do not describe every behavior in the current source. Check implementations before assuming a new capability is required.
- [CMake configuration](../../CMakeLists.txt) currently identifies the source version as `1.0.5` and defaults update discovery to `LoreanXavier/pt-pc`. The Git remote for this checkout is `spitefulFr0g/pt-pc`. The update ticket must account for both the launcher and existing in-game/updater entry points.
- The game accepts `--vr` and `--no-vr`; the latter can force a flat launch even when VR is enabled in saved settings. See [main.cpp](../../src/main.cpp) and [VR documentation](../../docs/vr.md).
- [OpenXR build configuration](../../cmake/OpenXR.cmake) enables VR by default only on Windows and acquires a package containing the Windows loader. The native Linux host has a `dlopen("libopenxr_loader.so.1", ...)` path in [xr_host.cpp](../../src/engine/xr/xr_host.cpp). This is evidence of a code path, not evidence that a native Linux VR build or a physical headset works.
- The game falls back to flat mode when VR initialization fails. Whether the launcher should permit that behavior after an explicit VR launch is an open UX decision.
- [VR documentation](../../docs/vr.md) says physical-headset validation has not been performed by upstream; existing simulated-runtime results do not establish hardware compatibility.
- [Settings types](../../src/engine/platform/settings.h) and [settings serialization](../../src/engine/platform/settings.cpp) define the game's current options. Launcher settings must preserve options it does not own, saves, and mods.
- The current [update checker](../../src/engine/platform/update_check.cpp) verifies embedded signed manifests against the public key from `release_key.h`; the alternate key is gated behind test overrides. Pointing the checker at another repository does not establish acceptance of independently signed downstream packages. [Existing updater orchestration](../../installer/Native/updater_core.h) and [installation inspection](../../installer/Native/setup_core.h) also assume the existing upstream program/manifest layout. The architecture decision must account for the adopted portable layout and downstream trust identity without modifying the game or using test bypasses in production.

During initial charting no game archives were inspected or copied. After charting, the user offered a real Windows Desktop export; [Windows Desktop export example](windows-export-example.md) records its read-only layout and format/identity probes. No game files have been copied into the repository. No launcher implementation or runtime validation has been performed.
